REVISÃO DA MODELAGEM — AQUICULTURA
==================================
Objetivo: manter os cadastros e consultas do sistema original e corrigir a
estrutura do banco com os conceitos das apostilas de Banco de Dados.

1. ANÁLISE DOS ATRIBUTOS
As tabelas originais foram preservadas. Espécies, tanques, fornecedores e
funcionários já tinham os dados necessários ao cadastro; não há necessidade
comprovada de acrescentar campos como capacidade, admissão ou limites
mínimos e máximos. O documento de fornecedor recebeu UNIQUE.

Lotes: fornecedor_id opcional, pois existe produção própria ou doação.
Registro de alimentação: alimentacao_id substitui lote_id. O lote já está
no plano de alimentação, evitando guardar a mesma referência duas vezes.
Registros de alimentação, água e mortalidade: funcionário opcional.
Tratamentos e manutenções: funcionário substitui o nome livre do responsável.
Manutenções: tanque_id ou equipamento_id substitui o texto livre do objeto.
Vendas: cliente_id substitui o nome livre. Data, documento e observações
continuam na venda. Lote, quantidade, unidade e preço ficam nos itens.
Clientes: id e nome (o nome já existia nas vendas).
Equipamentos: id, nome e tanque_id opcional (equipamento pode ser avulso).
Itens de venda: id, venda_id, lote_id, quantidade, unidade e preco.
O valor do item é calculado a partir da quantidade e do preço.

2. RELACIONAMENTOS E CARDINALIDADES
15 tabelas, 108 campos e 19 FKs. Todas as tabelas possuem uma PK id.
O primeiro par representa quantos registros da tabela principal um registro
filho pode ter; o segundo indica quantos filhos um registro principal pode
ter. FKs obrigatórias usam NOT NULL; as demais aceitam NULL.

tanques                 -> equipamentos            tanque_id           (0,1) : (0,n)
especies                -> lotes                   especie_id          (1,1) : (0,n)
tanques                 -> lotes                   tanque_id           (1,1) : (0,n)
fornecedores            -> lotes                   fornecedor_id       (0,1) : (0,n)
lotes                   -> alimentacao             lote_id             (1,1) : (0,n)
alimentacao             -> registro_alimentacao    alimentacao_id      (1,1) : (0,n)
funcionarios            -> registro_alimentacao    funcionario_id      (0,1) : (0,n)
tanques                 -> qualidade_agua          tanque_id           (1,1) : (0,n)
funcionarios            -> qualidade_agua          funcionario_id      (0,1) : (0,n)
lotes                   -> tratamentos             lote_id             (1,1) : (0,n)
funcionarios            -> tratamentos             funcionario_id      (0,1) : (0,n)
lotes                   -> mortalidade             lote_id             (1,1) : (0,n)
funcionarios            -> mortalidade             funcionario_id      (0,1) : (0,n)
funcionarios            -> manutencoes             funcionario_id      (0,1) : (0,n)
tanques                 -> manutencoes             tanque_id           (0,1) : (0,n)
equipamentos            -> manutencoes             equipamento_id      (0,1) : (0,n)
clientes                -> vendas                  cliente_id          (1,1) : (0,n)
vendas                  -> itens_venda             venda_id            (1,1) : (0,n)
lotes                   -> itens_venda             lote_id             (1,1) : (0,n)

Regras complementares: uma manutenção aponta para um tanque ou um
equipamento, nunca para os dois ao mesmo tempo. Uma venda pode conter zero
ou mais itens na etapa de cadastro; cada item tem exatamente uma venda e
um lote. Uma venda concluída deve ter pelo menos um item (regra operacional,
não imposta pela FK). Fornecedor de um lote é opcional e deve corresponder
à origem real do lote; o modelo não exige fornecedor para produção própria.

3. TABELA ASSOCIATIVA E NORMALIZAÇÃO
Venda e lote formam uma relação N:N quando uma venda reúne vários lotes.
A tabela itens_venda resolve essa relação com duas FKs, conforme o exemplo
pedidos/itens_pedido/produtos da apostila do 4º bimestre. Cada item guarda
sua quantidade, unidade e preço. Clientes, funcionários e equipamentos
são cadastrados separadamente. Cada campo guarda um valor (1FN); os dados
específicos de cada item ficam no item (2FN); dados descritivos de outras
entidades são recuperados por suas FKs, não copiados (3FN).

4. MODELOS E CÓDIGO
Conceitual: entidades, atributos próprios, losangos de relacionamento e
cardinalidades. O identificador está sublinhado; FKs aparecem no lógico.
Lógico: tabelas, campos, PK, FK, tipos e cardinalidades.
Físico: script MySQL com CREATE DATABASE, USE, CREATE TABLE, INT, VARCHAR,
TEXT, DATE, DATETIME, TIME, DECIMAL, PRIMARY KEY, AUTO_INCREMENT,
FOREIGN KEY, REFERENCES, NOT NULL, UNIQUE e CHECK.
UML: classe CadastroDAO e suas dependências reais, conforme o app.py.
As apostilas anexadas são de Banco de Dados, não de Python/UML. O código
original de Flask, PyMySQL, HTML, JavaScript e PHP foi preservado como base;
foram ajustados somente os campos, referências e formulários necessários.
Não se afirma que essas tecnologias foram ensinadas nas quatro apostilas.

7. VERIFICAÇÃO
A estrutura, as 19 FKs, as restrições e as sete consultas foram conferidas
em SQLite em memória, com adaptação de CREATE DATABASE, USE e AUTO_INCREMENT
apenas para o teste. Foram verificados os 15 formulários renderizados e a
validação Python com os dados de teste; JavaScript e PHP passaram na análise
de sintaxe. MySQL e Flask/PyMySQL não estavam disponíveis neste ambiente.
O teste final no XAMPP ainda é necessário. Nenhum banco anterior foi alterado.
